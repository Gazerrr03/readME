# 情報が、私の代わりに考え始めるとき

Published: 2026-08-09
Last edited: 2026-08-13
Tag: 设计

## 前書き

記憶が正しければ去年の八月、今でもあの ChatGPT に頼って学んでいた日々を忘れないだろう。それがあることを私に構想させたからだ。キャンバス上でのマルチブランチ対話は、従来の LUI の線形対話を取って代わるかもしれない、と。

だから Flow canvas という製品を作り始めた。

その過程で私は AI ワークフローの興隆と退潮を目撃し、Skill の登場を見、マルチエージェントが業界の技術的正しさになっていくのを眺めた。新しいものが次々と現れ、その速さは不安を煽るほどだった。振り返れば、純粋な LLM API 呼び出しにすぎない自分たちのものは、だんだん魅力がなく、かっこよくもなくなっていった。

いつの間にか Flow canvas は私たちの目にはかっこ悪くなっていた。それでも、この未熟なアイデアに情を抱き続けていることは認めざるを得ない。

そのために長い間もがいた。名状しがたい苦しみだった。生理的にも心理的にも実質的な痛みはないのに、苦しい。

私は大企業に履歴書を送り込み、テンセントに三度落ち、最後には自分で自分のチャンスを手放した。左右の脳が戦っているかのようだった。

大学三年間の努力を全否定し、創造の情熱さえあれば中退さえ構わないという理想主義にすがった。そのために、推薦入学を諦める口実まで自分で用意し、それを「好き嫌い」と呼んだ。

信じる自分と疑う自分を、何度も何度も往復した。

AdventureX ハッカソンに参加して、初めて「情報過多」の層に気づいた。Coding Agent はコードを書けない人にさえアイデアを実現する機会を与え、誰もが「かっこいいこと」をやりたいと言っていた。では、かっこいいとは一体何なのか。私はずっと二値的な思考でそれを理解していた。

しかし AdventureX がくれたのは焦りではなかった。逆に、再び鼓舞された。

それまではかっこいいものを作りたくてたまらなかったのに、本当のかっこよさを理解せず、「見た目がすごそう」を物差しに、延々もがいて、自分の行動にそれらしい理由を付けては、何だかかっこいい理屈を探していた。

ハッカソンに来て気づいたのは、かっこいいことをするのはそれ自体がロックだということ。壮大な何かとして包装する必要はない。

多くの若い参加者と話した。AI で一人の能力の境界を外へ押し広げようとしている人もいる。AI を技術の見せ物にせず、本当に自分の生活の問題を解決するために使っている人もいる。それらの問題は小さく、壮大なプロダクトストーリーに包装する価値すらないかもしれない。しかし確かに、誰かの生活のどこかを少しだけスムーズにした。

「かっこいい」とは、新しい用語やモデルやアーキテクチャを積み上げることではない、と改めて思った。

私の理想のギークとは、世界にかっこいいものを捧げたい人だ。誰もが当たり前だと思っているものを捉え直し、別の形がありうるのではないかと考え、その答えを自ら作り、誰かに使ってもらえるよう手渡す。かっこよさは自己表現だけではなく、アイデアを差し出したいという行動でもある。

Flow canvas はまさにそういう試みだ。思考キャンバスの形への再考であり、慣れ親しんだ LUI（Linear User Interface）への再検討でもある。ある特定のツールに自分を分類しようと急がず、まず一つのインタラクションの形を提示し、人々がそれで何をしたいのかを見る。

もちろん、この問いに標準解はないかもしれない。少なくとも今聞かれれば、こう答えるだろう。知識の高さに関わらず誰もが快適に扱え、誰もが平等に使え、それぞれの生活を少し便利にする製品。それこそが私の「かっこいい」の直感に合うものだと思う。

## ゴミ箱から、捨てた紙くずを拾い上げる

そして私は Flow canvas を拾い戻した。いや、本当の意味で心を込めて作り始めた。

この棚上げしていたアイデアを再び手に取ったとき、自分が情報過多に囚われていることに気づいた。

一年前の自分としてこの答案を解き直せるのが嬉しくて、チームでは「ルネサンス」と冗談めかして呼んだ。

受験生である以上、もちろん真剣だった。あの期間、Product Hunt で褒められている製品を片っ端から見て、キャンバスやノート、AI ワークスペース、デザインツールをたくさん見た。どの製品にも借りる価値があった。この製品のナビは心地よい、あの製品のカードは美しい、別の製品のレイアウトは仕事に向いている。一つひとつメモして Flow canvas に持ち帰り、自分の製品に収めようとした。

## ゴミはゴミ箱にあるとは限らないし、ゴミ箱にあるのはゴミとは限らない

新プロトタイプの構想の数日間、Flow canvas は確かにどんどん完成度が増していった。それらしい UI が増え、体験を良くしてくれそうなレイアウトも加わった。

しかしすぐに気づいた。それはごくありふれたキャンバス製品になっていくのであって、私が元々作ろうとしていたものではなかった。羽の生えかけの幼鳥が、拝借主義の頭で、森のきれいな鳥たちの羽根を自分の体に貼り付けているかのようだった。

本来なら、人々が Flow canvas を見たとき、特定の製品にすぐ分類されないことを望んでいた。マインドマップしか描けないのでも、画像をだらりと並べるだけのものでもない。ただ一つのインタラクションの形を定義する。ユーザーはカードを接続し、生み出せる。旅行の計画を立てることも、複雑なアーキテクチャを推敲することも、友人とテーブルトーク RPG を始めることもできる。

しかしケースをたくさん持ち込むほど、私が代わりに、それがどうあるべきかを決めてしまった。これは初期の考えと矛盾する。その頃は GenUI を導入して、各ユーザーが自分の作業環境に合わせて、自分に最も合うインターフェースの形を自ら育てられるかどうかを考えていた。キャンバスの中のカードはそれぞれ一台の車のようなもので、ユーザーが道に合わせて自由に改造できるようにする。

より良い答えを探していると思っていた。実際には、誰かがすでに与えた答えを探していただけだった。

## 「盗作者」が厚かましく自分の盗作を創作と定義するとき

似たような問題に出会ったのは、これが初めてではない。

大学で最初に高得点を取った課題は、ちょうど事例を調べることをまだ知らなかった時期のものだ。事前調査をまとめることも、デザインの巨匠を真剣に研究することもせず、彼らの記号を覚えて模倣するだけに留まっていた。ただ落ち着いて、曖昧な問題から始めて、Rhino でたくさんのボックスを作り、押して、引いて、動かして——実際のところ、創作の責任の多くをツールに外注していた。

幸運だったのは（論理もないのに美しいゴミを生み出せることを「運」と呼ぶことにしている。今のエージェントは、最低のプロンプトを与えても、いいカードを引き当てる確率があるからだ）、生成の過程は順調で、細部も前へ進み続けた。

先生は高い点をくれ、私は自分にデザインの才能があると思い込んだ。

今振り返れば、あのデザインは当然ロマンチックに語る価値はない。閉じこもって作ったもので、後に気づいたデザイン原則を本当には実践していなかった。運が良く、生成が滑らかな練習だっただけだ。しかしそれ以来、あんなに滑らかなデザインは一度もできていない。それはずっと私の記憶に残っている。

なぜなら、その後、調査を覚えたからだ。

私の観察では、デザイン教育はしばしば調査を非常に崇高な位置に置く。問題の定性すら終えていない学生に、まず事例を集め、資料を整理し、条件を分析するよう求める。積極的な調査はもちろん良いことだが、それは原点から問題を考えることに立脚すべきだ。さもなければ、調査は形式主義になりやすい。判断を検証するために資料を見るのではなく、資料そのものを判断として扱う。

行動レベルでは、学生は先生の要求のために調査し、自分でも意味が分からない資料を生み出し、それで一安心した気になってデザインに突入する。

これも私に起こった。

デザイン理論や事例を多く知り、検索能力も広がったと思ったときから、デザインは苦しくなった。ありうる「方向」を知りすぎたので、どの方向も十分に良く見えなかった。前期には案を作り続け、比較し続け、否定し続けた。

周りが手を動かし終える頃になって、深夜に自分を無理やり働かせ、疲れ果てた体からわずかな——それでも平凡な——創造を搾り出した。本質的にこれは売春婦と変わらない行為だ。

アイデアがなかったのではない。自分のアイデアが形になる前に、他人のアイデアを何本も部屋に入れてしまっていたのだ。

そして私は表現を本当に学べたことがなかった。思考は発散的で飛躍し、電波的に抽象的な観念をぽんぽん浮かべるのに、それを言葉にできない。それは仕事にも表れた。私は plan mode にかなり依存していたが、それはたいてい私の考えの部分的な蒸留にすぎなかった。AI とペア作業するとき、AI は必要な部分のコンテキストだけを取っていると思っていたが、実際は私にとってブラックボックスだった。本当に私の考えをすべて掴んだのか分からない。

## 溢れ出るコンテキストのポケットに、一体何を入れるべきか

情報過多とは、情報が多いことだけではない。

> より正確には、情報がいつ、現在の思考とどういう関係で入ってくるかを決める権利を、人から奪うことだ。

最近、友人から彼のブログ『Why Obelisk』を共有された。読んで感銘を受けた言葉が多い。特に検索の部分だ。検索そのものが、タイミング、範囲、権威についての判断である。少しズレた記憶、あるいは別の瞬間に属する記憶は、中立にコンテキストに入らない。現在の証拠と競合し、注意を奪い、古い結論を静かに現在の制約にしてしまう。

製品チームで情報過多を解決するのは、時に、より完全な資料庫を作ることでも、全員がすべての判断に参加することでもない。

taste のある人が、ある物事について十分明確な判断を形成し、確信のある結果を引き渡す用意があれば、他の人はそのために情報の帯域を消費する必要がない。これは中国の大企業でも見られる。未来のインターネット業界は、おそらく二種類の人に収斂するだろう。価値エンジニアと最適化エンジニアに。

これは情報伝達のエントロピーを減らすだけではなく、信頼を引き渡すことでもある。

『ナバル・ラビカン』にもある。リスクを引き受け、自らの名義で勝敗を引き受ける勇気こそ、大きな報酬と自主権を得るための唯一の道である、と。

「私はもう見ました。この結果で次へ進めます」という言葉の価値は、そこに含まれる情報量ではなく、他人の判断の一部を引き受けることにある。この信頼がなければ、チームは調査を繰り返し、説明を繰り返し、議論を繰り返し、本来前に進めるはずのことを情報の中に閉じ込めてしまう。

だから本当に大事なのは、全員に多くを知らせることではなく、それぞれにこう知らせることだ。何がすでに十分確定していて、何がまだ疑う価値があるのか、と。

## 推理分析、抽象的な蒸留、実践的な検証

私は調査に反対しているのではない。自分自身の問題をまだ形成していないうちに、調査に代わりに考えさせられることに反対している。

良い調査とは、予備的な判断への攻撃であるべきだ。盲点を見つけ、反例を見つけ、方向を校正し、抽象的な思考を理性的な「是/非」のマトリクスへ収斂させ、また自分の問題がそもそも明確に定義されていないことに気づかせてくれる。しかし最初から、問題が何かを規定してはならない。

さもなければ、よくあるデザインのプロセスが現れる。誰かが機能を持っているから、私もまずこの機能を持たなければならない。あるスタイルが多くの人に好まれるから、私の製品もこのスタイルを使うべきだ。あるケースが成功したことが証明されたから、それが私の思考の起点になる。

創作は盗作になる。

盗作は確かに、ゼロからの人を速く成長させる。すでに歩かれた道を提供し、一時的な完成感を与える。しかし、すでに基礎のある人を優秀に導くのは難しい。あなたが見ているのは、物事を細かく切り刻んだ後の記号にすぎない。その記号を組み直しても、結果はたいてい源の高さの下に留まる。

噴水が源より高くなることは決してない。ましてや、源がなぜそう流れるのか、私たちは往々にして理解していない。

『プロンプトをコードとして書くのか、ジャズとして弾くのか』で引用されていた研究を読んで、見透かされた気がした。「個人は強くなり、集合は狭くなる。誰もが自分の最高の水準を書くが、その最高の水準はどんどん似てくる」。AI 支援による文章の集団的収斂の話だったが、味わうほどに、他人のケースを自分の製品に貼り合わせる人も同じ穴に落ちていると思う。

ただしこれは教条的な規則でもない。大企業ではよくあることだ。市場にはすでに Trae があるのに、Codebuddy も居場所がある。豊富なリソースを背負えば、力業でも十分だからだ。

それでも私は「学ぶ」ということを定義し直したい。創作の本質と学習はあるレベルで同じであり、結局は I/O、平たく言えば「知行合一」だからだ。

パターンを真似るのは「蒸留」にすぎない。複数のパターンから規則を帰納し、それを応用できるようになって初めて「学習」と呼べる。

## 高次元の点は低次元の多くの線や面に投影されるが、投影は可逆でもある

借りること自体は問題ではない、と私はますます信じている。問題は、何を借りるかだ。

世界の一見まったく異なるものたちは、より巨視的なレベルでは同じ構造を持っているかもしれない。ゲームデザインのステートマシンは、エージェントのタスク状態を理解する助けになる。機械システムの信号伝達は、複雑なツール間の協調を考える助けになる。スタークラフトの編隊は、大きなキャンバスで空間を素早く整理する比喩になりうる。

こうした借り方は、外形を移すのではなく、関係を発見することだ。何が組織され、何が素早く呼び出せ、状態がどう変わり、フィードバックがどう伝わり、ユーザーが複雑なシステムの中でどう方向感を保つか。

大規模言語モデルはここで時に非常に価値がある。自然言語に強く、多くの観点をクラスタリングし、長く複雑なテキストをより明快な構造に圧縮し、異なる領域の共通点を見つける手助けもできる。しかし本当に助けになるのは、既製のスタイルを選んでくれることではなく、様々な現象の背後にある相似の関係を見せてくれることだ。

## 「主義」がディスクに焼けるものになるとき

デザイン界では、複雑な現象を数文字に圧縮する習慣がある。ミニマリズム、機能主義、ポストモダニズム。これには大きなコミュニケーション価値がある。一つの言葉で、同じ領域の人々が瞬時に文脈を揃えられる。

しかし圧縮には必ず損失があり、理解の城壁も築かれる。その主義を知らない人でも、ある神遊びの中で主義の背後にあるものに触れることはでき、全く新しい言葉を作ってそれを語ることさえできる。

同時に、私たちがその名詞に頼りすぎ、その歴史、問題意識、生成過程を辿らなくなるとき、「主義」は包装になっていく。現実への応答ではなく、呼び出せる視覚的なラベルへと変わる。

エージェントや様々なデザインスキルが、このことをいっそう明確にする。今や「アップル風のウェブサイトをください」と言うだけで、システムは丸み、余白、書体、ガラス、アニメーションを組み合わせ、一見完成されたデザイン説明を返す。

これは確かに多くの人に、見た目の良いインターフェースを作る能力を与えた。しかし見た目の良いインターフェースの背後には別の問いがある。本当にユーザーを理解しているのか。コミュニティでフロントエンドスキルを讃え、一日で何かのデザインを作れると自称する人たちは、なぜ Apple のデザインが誰にでも模倣でき、誰からも認められる価値があるのか、考えたことがないかもしれない。

どんなに精緻なスタイルテンプレートでも、捕まえるのはたいてい形だけだ。なぜエラーメッセージは数秒遅れて出るべきか、なぜある情報はこの瞬間に隠すべきか、なぜある動作は中断され、別の動作は連続のままであるべきか——答えられない。

これらは教条的な UX ルールではなく、人間の注意力、認知負荷、感情の変化、身体の習慣についての総合的な判断だ。実験、インタビュー、失敗、そして繰り返しの修正から生まれ、一つの Markdown 文書に完全にパッケージできるものではない。

だから Skill が下げるのは実行コストであって、判断コストではない。

実行が安くなるほど、taste はより明確にこう現れる。effort をどこに置くか、いつ止めるか、何を続ける価値がないか。

## AI ネイティブは力の入れすぎを推奨し、同時に推奨もしない

私は後に、エージェントの働き方にも同じ問題があることに気づいた。

プロジェクトの初期には、先入観で多くのことを考えてしまいがちだ。モデルの thinking effort を最大に上げ、plan mode を開き、コンテキストを可能な限り完全に用意する。前もって十分考えれば、後の回り道を減らせるかのように。

しかし多くの場合、実際の抵抗はまだ現れていないのに、想像上の抵抗のために大量の情報を用意している。コンテキストが長いほど、計画が複雑なほど、行動はむしろためらう。

もちろん、AI ネイティブな働き方は low effort ではない。可能な限り小さな effort の総量で、effort を本当の刃先に置くことだ。まず動かせる仮説を形成し、まず最も重要な部分を検証する。実際の抵抗に出会ってから、検索、計画、モデル、ツールを的を絞ってアップグレードする。

目標、価値、停止条件を決めるのは依然として人間だ。AI は巨視的な構造を見つけ、情報を圧縮し、いくつかの可能な方向を提示できるが、どの方向に進む価値があるかを決めるべきではない。

## 決める権利を取り戻す

今振り返れば、あの調査のない大学デザインが私の才能を証明したとは思わない。ただ、検索を覚える前の人は、少なくとも問題そのものから考えることを強いられる、ということを示しただけだ。

本当に変えるべきなのは、調査を拒むことでも、借りることを拒むことでも、Skill や AI を拒むことでもない。

自分自身の問題を形成する前に、それらに代わりに考えさせることをやめることだ。

原点から判断を形成してから、世界を入れよ。続ける価値のある方向を見つけてから、effort を注ぎ込め。

> 私たちに必要なのは、より多くの情報ではなく、情報がどのように自分に入ってくるかを決める権利を取り戻すことかもしれない。

[Why Obelisk（なぜオベリスクなのか）](https://kinomotomio.github.io/writing/why-obelisk/) — kinomotomio。taste、context vibe、そして「良い Skill はすでに成功した協働から発掘されるものであって、前もって発明されるものではない」ことについて。実行コストと判断コストを区別する助けになった。

[プロンプトをコードとして書くのか、ジャズとして弾くのか](https://mp.weixin.qq.com/s/H0vmaXUVRA7rmDAF_kgZ9A) — WeChat 公式アカウント。PromptOps と PromptJazz という二つの人機協働スタイル。本当に希少なのは、プロンプトの書き方ではなく、十の候補から正しい一つを選ぶことだ。

## Mem0「In Context」シリーズ

[Beam Memory Benchmark: Key Findings on 1M Context](https://mem0.ai/blog/what-is-beam-memory-benchmark-the-paper-that-shows-1m-context-window-isnt-enough)（In Context #2）— 1M トークンのコンテキスト窓は、より良く覚えることを意味しない。本当のボトルネックは、情報がどう保存・更新・使用されるかにある。

[How Memory Works in Claude Code](https://mem0.ai/blog/how-memory-works-in-claude-code)（In Context #4）— Claude Code の記憶メカニズムの分解。200 行のインデックス、静かな切り詰め、バックグラウンド抽出。AGENTS.md はあまり変わらない規約を載せるのに適していることも説明している。

[Dream: Background memory consolidation for AI agents](https://mem0.ai/blog/dream-background-memory-consolidation-for-ai-agents) — Mem0 がエージェントに与える「睡眠」。重複を統合し、陳腐化を印し、散在する事実をより上位の記憶へと帰納する。そして何も直接は削除しない。

[Beyond AGENTS.md: Shared Memory for Coding Agents Across Services and Repos](https://mem0.ai/blog/beyond-agents.md-shared-memory-for-coding-agents-across-services-and-repos) — AGENTS.md は「ここでのルールは何か」に答え、共有記憶は「前回誰かが見てから、何が変わったか」に答える。
