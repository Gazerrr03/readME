# 情熱が私を出発させ、失敗が境界を見せ、責任が私を進ませる

Published: 2026-08-24
Tag: AI

この夏、どこへ行っていたのかと聞かれたら、たぶんこう答える。独立プロダクトを作っていた、と。

周りの人からすれば、少し「本業から外れた」答えに聞こえるかもしれない。卒業を目前にした最後の夏、私は就職活動のためのインターン経験を積むことも、大学院進学のための研究経験を補うこともしなかった。その代わりに、考え始めてから一年が経つのに、いまだにまともな答案を提出できていない Flovvas に時間を使った。

私は、何の光輪もない状態でこの選択をした。インターンの実績という裏付けも、研究成果という手すりも、すでに有効だと証明された肩書きもなかった。

なぜそれをしたのか、私はまだ十分に整理された答えを持っていない。

自分の手でアイデアを生み、何もないところから芽生え、形になるまでを見届けたかったのかもしれない。Artificial Intelligence（AI） Agent の時代が加速するのを目撃し、数日のうちに「椅子に座り込んだまま、原子爆弾の爆発を見たような」瞬間が次々に現れることに興奮したのかもしれない。あるいは、まだ照らされていない場所や、解決を待っている問題がこの世界に残っていて、デザイナーを自称する自分にも、そこへ関わる責任があると感じたのかもしれない。

理由は違って見えるけれど、たぶん同じことを指している。不確実性の中へ入り、自分に何ができるのかを自分の手で確かめたかったのだ。

## 情熱が先に決めてしまった

Flovvas の最初のアイデアから、もう一年が経った。答案を振り返ると、何度も書き直した跡が見える。計算を書いては消し、方向を決めては疑い、答えに近づいたと思った次の瞬間には、問題の名前を変えただけだったと気づく。

AI（Artificial Intelligence）が創造にもたらした繁栄に、私たちは興奮した。かつてはほとんど不可能だったことが、一つの文章から始められるようになった。大学一年のころから、卒業までに自分のウェブサイトを作りたいと思っていた。いまなら coding agent に一言伝えるだけで始められる。

しかし、ゼロから一を作ることが簡単になったからといって、成功が簡単になったわけではない。本当に難しいのは、何かを作ることよりも、それが作る価値のあるものか、ユーザーの行動を変えるのか、価値がないときに止まれるのかを判断することだ。

それでも不確実性の波へ乗るのか。その問いは、熱狂だけでは答えられない。波の中には失敗の獣が潜んでいる。

> It waits. Patient.

獣は辛抱強く待っている。獲物はいつか必ず現れると信じている。多くの新しいプロダクトは噛みつかれる。経験や能力や準備が、永久の免疫証明書になることはない。

現実は残酷だ。不確実性に必勝法はない。「上岸」、つまり安全な岸へたどり着いたという感覚も、まだ見えていないリスクに名前をつけただけかもしれない。これは就職、大学院、研究を否定する話ではない。どの選択も、失敗の可能性を私たちの代わりに消してくれるわけではない、という話だ。

そういう意味では、「上岸」そのものが一つの嘘なのかもしれない。岸が存在しないのではなく、出発する前に自分が安全だと証明することはできないからだ。

それでも、熱が残っているのはよいことだ。何年も後に学校を出て、生活と本格的に向き合うようになったとき、私は今日を振り返って、この車に乗らなかったことを後悔するだろうかと考えるかもしれない。AI の初心者として ChatGPT のプロダクト体験を疑い始めたころ、紙に描いた初期の構想をまだ覚えているだろうか。

情熱は最初の一歩を踏み出させ、責任を引き受けさせる。でも初期の段階では、その人の能力が引き受けた責任の大きさに届いていないこともある。情熱を否定するのではなく、出発のあとに責任に見合う能力を鍛えられるかが問われる。

## Adventure X で見た「ゴミを作る」こと

七月末、今年の Adventure X ハッカソンに参加した。そこには面白いアイデアを持つ人たちがいた。OPC（One Person Company）を本当に実践し、「毎月百個のゴミを作る」と冗談を言う人もいた。特定の領域に突出した人もいた。あるデザインの選手を二時間後ろから見ているだけで、同じ時間なら自分より多く、価値のあるものを届けるだろうと信じられた。

特に印象に残ったのは、デザインを専門にしている選手だった。彼の後ろに座り、二時間デザインをしている姿を見ているだけでも心地よかった。美意識とさまざまなコンポーネントライブラリへの習熟を見ていると、能力が形成されたあとには、速さそのものが一種の品質になるのだと感じた。同じ二時間なら、彼は私より多く、より価値のあるものを届けるだろうと心から思った。

印象に残ったのは、単に速かったことではない。未完成のものを現実の前に置き、何を続ける価値があるのかを現実に教えてもらう勇気があったことだ。

「ゴミを作る」は、雑に低品質なものを出すという意味ではない。OPC を一人で運営する人にとって、それは実践をフィードバックの生産システムとして扱うことだ。ビジュアルデザインでゴミを作るのは安いかもしれない。しかしプロダクトエンジニアリングでゴミを作るのは難しく、そこには技術がいる。

彼らはみな極客だった。私にとって極客という言葉は、最初から「クール」と一体だった。彼らを見たことで、この夏、自分のプロダクトにももっと真剣に向き合う力をもらった。

## 情熱と責任が初めて衝突した

開発段階に入ると、私は最初、情熱は持っていたが、十分な思考と分析を持っていなかったことに気づいた。これは四月に Zhiyan を作ったときにも犯した失敗だった。情熱は責任を引き受けさせるが、責任を果たしてはくれない。

だから自分への批判は厳しくしたい。努力していたからという理由で、うまくできなかった努力を慰めの美徳に変えたくない。

私は開発スケジュールを細かく組み、要求、feature、issue をたくさん書いた。しかし価値、レバレッジ、エンジニアリングコストへの判断が足りなかった。計画が詳しくなるほど、優先順位は見えなくなった。

feature の設計では情報過多に陥った。プロダクトの核心 loop と関係の薄いことまで考えたのに、それらを熱挿抜できるモジュールにする発想がなかった。新しいアイデアが、システムへの永久の約束になっていった。

プロダクトの構想会議でも、話したい欲望にブレーキをかけられなかった。今のバージョンと関係のないことまで広げ、すでに複雑な用語をさらに混乱させ、本来なら三十分で終わる会議を長引かせた。

一番具体的な結果は、issue を書き上げたのに、それがチームで問題を共有理解する器ではなく、みんなの coding agent subscription を借りるための通行証になったことだ。偏ったコンテキストを持つ issue もあり、その偏りは開発を重ねるほど増幅された。

つまり、努力し、時間と token を使った。それでもプロダクトが前進したとは限らない。

大学教育は、こうした努力を美化しがちだ。授業で勤勉に見えれば平常点をもらえ、休暇中に学校に残って大会を準備すれば広報記事になる。私もそういう人だった。努力が悪いのではない。結果がなくても努力さえすればよいと信じると、より本質的なものが見えなくなることが嫌なのだ。AI によって手作業が安くなるほど、労働だけでは価値の証明にならない。

## エンジニアリングの「ゴミ」が難しい理由

人はエンジニアリングでゴミを作らないようにする。だから早い段階で完璧なものを想像しようとする。しかしその完璧な想像は未検証の仮定を隠し、捨てにくい低価値の仕事を生む。

エンジニアリングのゴミとは、雑な仕事ではない。境界があり、安く、取り消せて、現実のフィードバックを買うための失敗サンプルだ。

ビジュアルデザインでは十案を作って九案を捨てても、主なコストは時間かもしれない。プロダクトエンジニアリングでは、一つの「ゴミ機能」がコード、データ構造、保守コスト、コンテキスト負債、チームの誤解を残す。削除ボタンを押しても本当に消えるわけではない。

だから、何を素早く試すか、何を取り消せる範囲に閉じ込めるか、どの信号が出たら投資を止めるかを判断しなければならない。

私たちは後に、「一人がすべての要求を定義し、issue に分解し、配る」やり方より、チームで一つのバージョンのレバレッジ要求を決め、それぞれが一つの要求の定義、開発、検証を持つほうがよいと気づいた。

ここでいうレバレッジとは、なくなればユーザーがすぐ離れる機能、またはあればユーザーを増やせる機能だ。単にクールに聞こえるものではなく、プロダクトの生存確率を変えるものだ。

これは各自を孤立した小さな会社にすることではない。各自が、その feature の線でユーザーに何をさせ、何を感じさせるのか、なぜ作る価値があるのかを知ることが前提だ。実装は各自の Agent が探せる。しかし結果への責任は分割できない。

『人月の神話』に出てくるランス大聖堂の例を思い出す。全員が同じ大聖堂を建てる建築家だ。もし一人ひとりに思考のスイッチがあるなら、重要なのは考えるかどうかではなく、常にオンにしておくべきかどうかだ。方向を疑い直すときと、発散を閉じて決まったものを仕上げるときを知る必要がある。

Less is more は、単に機能を減らすことではない。不要な約束、分岐、認知ノイズを減らし、荷重を支える構造を立たせることだ。建築にも、ソフトウェア工学にも、Agent engineering にも、仕事の知恵にもつながっている。

## AI は learning と doing を切り離した

AI に興奮するのは、learning と doing の分離が加速したからだ。より AI-native な方法で learning by doing を実践し、知識と経験を早く得られる。

世界を多次元空間として想像することがある。観測し学んだものは、その中のサンプル点だ。高次元から見ると共通の構造を持つかもしれない。大規模言語モデルは言語を扱い、異なる点から共通の視点を圧縮するのが得意なので、以前は結べなかった関係を見せてくれる。

しかし危険でもある。learning だけで doing がなければ、知識は経験へ流れない固定記憶になる。doing だけで learning がなければ、未検証の経験が蓄積し、誤った一般化が教条になる。

私は長く後者にいた。多くのことをしたのに、記録せず、理論で検証し直さなかった。この夏、ブログを書き、自分の経験を記録し、本を読むようになった。特に失敗した実践を持って成熟したプロダクトデザインの方法を見ると、読書は暗記ではなく、自分の経験を再解釈することになる。

これは、地動説がまだ提案されていなかったころ、人々が目の前の現象から天動説を導き、それを教条として扱うようになったことにも似ている。AI は資料を圧縮し、案を生成し、視点をつなげられる。しかし一手の経験を与えたり、その経験が本当に現実から来たものかを判断したりはできない。learning と doing は、私たち自身が同じ循環に戻さなければならない。

## 単純な問題と複雑な問題

AI がこの可能性を与えたからこそ、私は問題を単純なものと複雑なものに分けて考え始めた。厳密な世界分類ではなく、実践に役立つモデルだ。

単純な問題では変数の多くを制御できる。正しい思考と時間があれば、成功確率を大きく上げられる。大学院試験の準備はかなり単純な問題だ。目標、範囲、評価、フィードバックが比較的明確なので、本質を分析し、行動を設計できる。

Agent engineering にも同じ部分がある。式にするなら Agent loop + Context + hooks = Agent だ。多くの要素を制御、交換、テスト、再構成できる。DeepSeek harness は Agent のコンテキストのライフサイクルを操作し、入力と出力をより交換可能なモジュールにする可能性を示した。

しかし、プロダクトを作るべきか、ユーザーが残るか、デザインが現実の生活で成立するかは単純ではない。

GalGame でヒロインを攻略するのは、たいてい単純な問題だ。現実の人と恋に落ちるのは複雑だ。前者には設計された変数、フィードバック、ルールがある。後者は天気、距離、身体、偶然、そして別の人の自由意志に変えられる。

デザインも複雑な問題だ。視覚変数だけではなく、感情、状況、文化的経験、遅れて届くフィードバックが関わる。賢い SOP がまだ見つかっていないのではなく、完全には制御できない変数を含んでいるのだ。

複雑な問題は目の前の山で、一度には越えられない。複雑さは消えないし、消えたふりをする必要もない。より観察しやすく、検証しやすく、協働しやすい場所へ移せばよい。

ソフトウェアが柔軟なのは、「完璧なシステムを構想する」複雑さを、一つひとつの具体的な問題へ移せるからだ。ウォーターフォールから小さな Sprint へ移るのは、考えることをやめるためではない。フィードバックのない白紙より、現実の失敗結果のほうが考えやすいからだ。

## 情熱のあとにある責任

情熱のあとにあるものは何か。私は責任だと思うようになった。

AI-native なチームでは、これからモデルの能力が高まり、一度に出力できる量が増えるほど、誰かがこう言う必要がある。「この内容は review した。問題はない。もし何か起きたら、自分が責任を引き受けて戻って処理する」。チームの全員がその可能性を持てば、チームはもっと遠くまで進める。

責任とは全知全能のふりをすることではない。モデルの出力を無条件に保証することでもない。自分の判断範囲を明確に示し、その判断の結果を引き受けることだ。

これは、全員に間違えないふりを求めることではない。一人ひとりの判断をチームが共同で建てる構造の中に置き、判断を誤ったときには戻って修正することを求めるのだ。

独立プロダクトを作ることが「本業から外れている」と感じる理由も、ここにある。私は Flovvas の初期コンセプトを考えた人ではある。でも、Co-founder と呼ばれるに足る境地にはまだ遠い。

いまはそれを神秘的な資格だとは思わない。Co-founder は、先に「ふさわしい」と証明する証明書ではない。問題を定義し、トレードオフを選び、定義から検証まで結果を持ち、うまくいかなかったときにモデルやチームや環境へ責任を押し戻さない、という行動の積み重ねだ。

自分が最も光る貢献領域を早く見つけ、そこでより大きな責任を持ちたい。デザインなら、短時間で美しいものを作り、ユーザー体験とフロントエンドのインタラクションの taste を磨き続ける必要がある。プロダクトなら、物事の本質を素早く分析し、要求の価値を素早く判断する必要がある。貢献領域は自分で貼るラベルではなく、結果で証明し、責任によって広げていく領域だ。

この理解で落胆はしていない。以前は、どうすれば合格した Co-founder になれるのかと悩んだ。今は、努力し、力を入れすぎ、たくさん失敗した自分に感謝している。失敗は能力の境界と、次に鍛えるべきものを見せてくれた。

## 失敗の獣へ：まだ飼いならせてはいない

『正しいものを正しくつくる』の序文には、少し中二病的に聞こえるかもしれないが、本当にかっこいいと思う一文がある。

> 失敗の獣へ：
あなたは私に多くの教訓を教えた。今度は私があなたを飼いならす番だ。

私の情熱は、この失敗の獣を飼いならそうと私を動かしている。獣は私に多くの傷跡を残した。でもその傷跡を手がかりにして、自分がまだ何を鍛える必要があるのかを見つけられる。

その感覚を、私は精神的な報酬に変えられるようになった。宮崎英高のゲームでボスに何度も倒され、それでも最後には相手の動きを読み、一つひとつの攻撃をかわし、ついに倒すときの感覚に近い。失敗は「自分には足りない」という判決ではなく、攻撃がどこから来るのかを示す地図にもなる。

チームに迷惑をかけたことへの罪悪感はまだある。でも罪悪感は、自分を罰するだけに使うべきではない。これから同僚と働くとき、罪悪感で努力するのではなく、実際にもっと責任を引き受けたいという願いに変えたい。

現実のフィードバックにも、もっと積極的に身をさらしたい。周囲が pi Agent を称賛しているのを見て、それがなぜ優れているのかわからない人は、先に学び、試し、一次経験から理解すればいい。最初は盲従に見えた人が、実践を通して pi Agent の本質を本当に理解することもある。

これは盲従の勧めではない。逆に、pi Agent が称賛されているのを見て、最初から「ただのバズワードだ」と決めつけ、試しもせずに傍から批評し続けるなら、道具だけでなく、実践によって自分の判断を修正する機会も逃してしまう。

そういう人は、むしろ愤青に近い。本当の文学的な気質や独立した判断ではなく、記号への同意と反発のところにとどまっている。判断力は、自分で作り、現実に試され、他人に反論される可能性まで引き受けることから生まれる。

だから私は、まず走り、作り、他人に評価してもらい、その評価を恐れないようにしたい。もっと積極的に自分を傷つけ、そこから成長したい。「傷つく」とは痛みを求めることではない。現実のフィードバックに身をさらしながら、失敗を回復できる範囲にとどめることだ。小さく、回復可能な失敗を意図的に受け入れるほうが、傷つかない結論を待ち続けるより、本当の経験に近づける。

## 歩き続ける

情熱が私を出発させ、失敗が境界を見せ、責任が私を進ませる。

この時間の教訓を吸収し、失敗を恐れず、従順な人を演じず、自分の能力の範囲で引き受けられる責任のしきい値を上げたい。極客になる道の上で、成長を続けたい。

私はまだそれを飼いならしていない。でも、どこから噛みついてくるかもしれないのかはわかり始めた。そして、自分が何を鍛える必要があるのかもわかり始めた。
