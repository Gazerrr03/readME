# 热情让我出发，错误让我看见边界，责任让我继续

Published: 2026-08-24
Tag: AI

如果有人问我，今年暑假去了哪里，我大概会说：我去做了一个独立产品。

这个答案在周围人听来，多少有一点“不务正业”。临近毕业的最后一个暑假，我没有去积累实习经历、准备秋招，也没有去补充科研经历、准备保研，而是把时间投进了 Flovvas——一个从想法萌生至今已经一年，却还没有交出一份像样答卷的产品。

从腾讯实习回来之后，我才慢慢意识到，自己其实一直在依赖某种光环：那段经历带来的背书、外界的认可，以及一个看起来已经被证明可行的身份。现在，我想把这些都从前提里拿掉，在不借助任何光环的情况下做这件事，看看自己究竟能不能把它做出来。

至于为什么要做这件事，我其实一直没有组织出一个足够清晰的答案。

也许是因为我想亲手孕育一个创想，看着它从无到有、从萌芽到诞生，体验那种接近创造生命的悸动与热情；也许是因为我见证了 AI Agent 时代加速到来，隔几天就能看到一些让人“瘫坐在椅子上，仿佛目睹原子弹爆炸”的时刻，意识到这个时代还有许多未知的可能等待探索；也许是因为我看见这片大地上依然有很多没有被照亮的角落，仍有很多问题等待解决，作为一个自诩设计师的人，我很难对那份想参与改变世界的责任感视而不见。

这些理由听起来各不相同，但它们或许都指向同一件事：我想进入一片没有必胜路线的不确定性里，亲手确认自己究竟能做什么。

## 热情先替我做了决定

Flovvas 距离最初的想法已经一年了。回头看这份答卷，能看出我们在上面经历了很多次涂改：写下计算步骤，又划掉；提出一个方向，又怀疑它；刚刚觉得终于接近答案，下一刻又发现自己只是把问题换了一个说法。

我们兴奋地迎接 AI 为创造带来的一片欣欣向荣。它让很多过去几乎不可能完成的事情变得可能：我大一时就想在毕业时搭建一个个人网站，而现在，有了 coding agent，类似的任务甚至可以从一句话开始。

但从零到一变得容易，并不等于成功变得容易。真正困难的，往往不是把一个东西做出来，而是判断它是否值得被做出来，是否真的改变了某个用户的行为，以及在它没有价值时能不能及时停下来。

既然如此，我们要不要选择去这片不确定性里冲浪？这个问题不能只靠热血沸腾来回答。因为失败之兽就蹲伏在浪潮里。

> It waits. Patient.\
> Confident that it will soon get its prey—it always does.\
> Few escape its bite, none its tentacles.\
> One way or another, the Beast of Failure gets us all.

它耐心地等待，自信地相信猎物迟早会出现。大多数新产品都可能被它咬住；经验、能力和准备并不能让任何人获得一张永久免疫的通行证。

现实自然是残酷的。不确定性里不存在必胜之法，所以“上岸”本身很多时候只是一种暂时看不见风险的说法。这里的意思不是反对实习、秋招、考研或保研，而是承认：任何一种选择都不能替我们彻底消除失败的可能。

甚至可以说，“上岸”本身是一句谎话——不是说岸不存在，而是我们无法在出发之前证明自己已经安全。

好在现实还有另一个角度。面对这个选择，我们仍然保有热情沸腾的余地。多年以后，当我正式从学校走到社会，开始成为一个真正要和生活对线的人，我可能会回望今天，问自己：我会不会后悔当初没有登上这辆车？我还能不能想起，自己作为一个 AI 小白，开始质疑 ChatGPT 的产品体验时，曾经在纸上勾勒过哪些早期构思？

热情可以让人踏出第一步，也可以让人主动认领一项责任。但在早期，一个人的能力可能还不足以承担过大的责任；热情并不保证他有能力把这项责任落实好。真正的问题不是因此否定热情，而是出发之后，能不能尽快训练出与责任匹配的能力。

## 我在 Adventure X 见到的“造垃圾”

七月底，我参加了今年的 Adventure X 黑客松。在那里，我见到了一些很有趣、也很有想法的人。有人真正实践着 OPC（One Person Company），笑称自己提倡每个月生产一百件垃圾；有人在某个独立领域里非常突出，两个小时里做出的设计数量和质量都让我相信，他可以远远超过当时的我。

我尤其记得一位专精设计的选手。哪怕只是坐在他身后，看着他在两个小时里完成设计，也是一件赏心悦目的事情。他对审美和各种组件库的熟练，让我直观感受到：同样是两个小时，能力形成之后，一个人不仅能交付更多，也能交付更有价值的东西。我完全相信，他当时能比我做得更多、更好。

但“每个月生产一百件垃圾”这句话真正让我有感触的地方，不是鼓励人随便输出，而是它把实践看成了一个持续产生反馈的系统。对于独立经营 OPC 的人来说，造垃圾从来不只属于某一个工作域。视觉设计里造垃圾可能很简单，产品工程里造垃圾却很难，也很有学问。

他们都是极客。在我看来，“极客”这个词本来就和“酷”连在一起。我之所以被他们鼓舞，不只是因为他们做得快，而是因为他们愿意把尚未完美的东西放到现实面前，让现实告诉自己什么值得继续。

也正是见到了这些人，我获得了更多动力，想在这个暑假把自己的产品再认真打磨一次。

## 热情和责任第一次发生冲突

正式进入开发阶段后，我很快发现，自己起初只是带着热情做事，却没有带足够多的思考和分析。这其实是我在四月做 Zhiyan 项目时犯过的老毛病。热情可以让一个人主动认领责任，却不能替他把责任完成。

所以我对自己的批评会很严厉。我不想因为自己确实努力过，却没有把事情做好，就把努力重新包装成一种值得安慰自己的美德。

我曾经把开发任务排得非常详细，列出了很多需求、feature 和 issue，却缺乏对价值、杠杆和工程代价的判断。任务越列越多，计划看起来越完整，开发流程反而越失去主次。

我在 feature 设计里也让自己陷入了信息过载：探讨了太多和产品核心 loop 关联很弱的内容，却没有想办法把这些内容做成高度可热插拔的模块。于是每一个新想法都像是一次对系统的永久承诺。

在团队的产品构思会议上，我还没有克制自己的表达欲。我不断发散，提出很多和当前版本无关的内容，让本来就复杂的术语变得更加混乱，也让一场原本半小时可以结束的会议继续拖长。

最具体的结果是，我把 issue 都写下来了，但这些 issue 最后更像是租赁大家 coding agent subscription 的通行证，而不是团队共同理解问题的载体。有些 issue 甚至带着偏误的上下文，而这些偏误又在多轮开发里被不断放大。

说白了，我努力了，用功了，消耗了大家的时间和 token，但这并不等于产品因此向前走了。

很多大学教育会过度美化这种用功：平时课程里表现得努力刻苦，就能得到更多平时分；放假留校准备比赛，就可能被写进学校公众号。我曾经也是这样的人。这样的自己让我厌恶，不是因为努力本身有错，而是因为一旦过度相信“只要努力了，哪怕没有结果也无所谓”，就永远看不到更本质的东西，也永远无法获得承担更多责任的能力。尤其在 AI 让许多手工劳动变得更廉价之后，劳动本身越来越不能成为价值的证明。

## 工程上的“垃圾”为什么很难造

上面这些经历让我重新理解了“造垃圾”。人在做工程时，通常会本能地避免制造垃圾，于是会试图在很早期就设想出一个自认为完美的东西。问题是，这个完美的设想往往隐藏了大量未经验证的假设，最后让我们在路上做了很多价值很低、却很难丢弃的工作。

工程上的垃圾不是粗制滥造，也不是把责任交给运气。它更像一种有边界、低成本、可撤销，并且能够换来真实反馈的失败样本。

视觉设计里，做出十个方案、丢掉九个方案，代价可能主要是时间。但产品工程里的每一个“垃圾功能”，都可能留下代码、数据结构、维护成本、上下文负担和团队误解。它不是点一下删除就真的消失了。

因此，工程上的造垃圾需要同时判断三件事：什么值得快速试，什么必须被限制在可撤销的范围里，以及出现什么信号后应该立即停止继续投入。

我们后来发现，早期那种“由一个人定义所有需求、拆分 issue、再分发 issue 开发”的方式，并不如另一种方式有效：团队先共同确定一个版本里的杠杆需求，再由每个人独立负责一个需求的定义、开发和验证。

我当下理解的“杠杆”是：一个功能一旦没有，用户可能马上离开；或者一个功能一旦有了，就可能为产品吸引更多用户。它不是“听起来很酷”，而是会改变产品生存概率的东西。

后者并不是把所有人都变成各自为战的小型公司。它的前提是，每个人都知道这条 feature 线路最后要让用户完成什么、感受到什么，以及为什么值得被做出来。实现方式可以由每个人和自己的 Agent 去探索，但结果的责任不能被拆散。

这让我想起《人月神话》里兰斯大教堂的例子。团队里的每个人都像是在搭建同一座大教堂的建筑师。但假使每个人身上都有一个思考开关，真正重要的问题就不是要不要思考，而是这个开关是否应该一直打开：什么时候需要重新审视方向，什么时候需要收起自己的发散，把已经确认的部分做好。

Less is more 在这里不是简单地少做功能，而是减少没有必要的承诺、分支和认知噪音，让真正承重的结构站出来。它可以映射到建筑，也可以映射到软件工程、Agent engineering，以及一个人的工作智慧。

## AI 让 learning 和 doing 分开了

AI 的出现让我兴奋，是因为它加速了 learning 和 doing 的解耦。我们可以用更 AI-native 的方式 learning by doing，更快地掌握知识和经验。

我有时会把世界想象成一个多维空间。我们观测到、学习到的东西，是这个空间里许多不同的采样点；从更高维的角度看，它们可能拥有共通的结构。大语言模型擅长处理自然语言，也擅长从不同采样点中压缩出共同视角，所以它让我们有机会看见一些过去难以连接的关系。

但这件事同时也是危险的。只顾 learning，不注重 doing，知识会变成固定的记忆，无法流通成经验；只顾 doing，不注重 learning，则会积累大量未经验证的经验，最后把错误的归纳当成教条。

我觉得自己曾经长期处在后一种状态里：做了很多事，却没有认真记录，也没有把错误放回理论里重新检验。好在这次暑期实践里，我开始被鼓励写博客，记录自己的所思所想和经验，也开始被鼓励读书。我可以带着实践，尤其是带着错误的实践，去看成熟的产品设计方法；这样的阅读不会只是记忆，而会变成一次对自己经验的重新解释。

这有点像日心说还没有被提出时，人们会根据眼前的现象得出地心说，甚至把它奉为教条。AI 可以替我们压缩资料、生成方案、连接观点，却不能替我们获得一手经验，也不能替我们判断哪些经验真的来自现实。这个判断仍然需要我们把 learning 和 doing 放回同一个循环里。

## 简单问题与复杂问题

也正因为 AI 提供了这样的可能性，我开始尝试把问题分成简单问题和复杂问题。这不是一个严格的世界分类法，只是一个对实践有帮助的区分。

简单问题的变量基本可控。只要拥有正确的思维指导，并且投入足够的时间，就能显著提高做成它的概率。考研在很大程度上属于简单问题：考试的目标、范围、评价方式和反馈周期都相对明确，因此可以分析它的本质，再据此设计行动。

Agent engineering 也有相当一部分属于这类问题。用一个公式表达，就是 Agent loop + Context + hooks = Agent。它的许多组成部分都可以被控制、替换、测试和重新组合。DeepSeek harness 的出现，则进一步让人们能够操作 Agent 的上下文生命周期，把输入和输出抽象成更容易热插拔的模块。

但产品该不该做、用户是否愿意留下、一个设计在真实生活里是否成立，就没有这么简单了。

在 GalGame 里攻略一个女主，通常是简单问题；在现实里和一个真实的人恋爱，却是复杂问题。前者的变量、反馈和规则是被设计出来的，后者会被天气、距离、身体状态、偶然事件和另一个人的自由意志不断改变。

做设计也是复杂问题。它不只是把几个视觉变量调到合适的位置，还涉及人的感受、使用情境、文化经验和滞后的反馈。很多问题不是因为我们还没有找到足够聪明的 SOP（Standard Operating Procedure），而是因为它本身就包含不可控的变量。

复杂问题像一座山摆在面前，几乎不可能一次性逾越。但复杂度自始至终都不会消失，也没有必要假装它已经消失。我们能做的，是把它转移到更容易观察、更容易验证、更容易协作的地方。

软件工程之所以灵活，正是因为它允许我们把“构思一个完美无缺的软件”这件事的复杂度，转移到一个个具体问题上。瀑布式开发转向 Sprint 小步快跑，并不是因为人们突然不想思考了，而是因为面对一个真实的失败结果，往往比面对一张没有反馈的白纸更容易思考。

## 热情之后是责任

热情之后是什么？我现在越来越觉得，是责任。

尤其是在一个 AI-native 团队里，当未来的模型能力越来越强、能够一次性输出越来越多的内容时，一个人如果能大胆地站出来说：“这个内容我 review 过，这个内容没有问题；如果出了问题，我愿意承担责任并回来处理。”那么，假使团队里的每个人都具备这样的潜质，这个团队就有可能走得更远。

责任不是假装自己全知全能，也不是对模型输出做一个没有条件的担保。责任是清楚地标记自己的判断范围，并且愿意承担判断带来的后果。

这并不是要求每个人假装自己不会犯错，而是要求每个人都愿意把自己的判断放到团队共同建造的结构里，并在判断失误时回来修正它。

这也回答了我为什么会觉得，自己做独立产品听起来像一件“不务正业”的事情。虽然我是 Flovvas 早期的概念构想者，但我知道自己还远远没有达到一个 Co-founder 应该达到的境界。

现在我对这件事的理解没有那么神秘了。Co-founder 不是一张需要先证明自己配不配的身份凭证，而是一组持续发生的行为：能够定义问题，能够做取舍，能够从定义一路负责到验证，也能够在结果不理想时不把责任推回给模型、团队或环境。

我需要尽快找到自己最能发光发热的贡献域，并且在那个贡献域里承担更大的责任。如果我的贡献域是设计，我就需要拥有在短时间内做出精美设计的能力，也需要不断打磨用户体验、打磨前端交互的 taste；如果我的贡献域是产品，我就需要拥有快速分析事情本质、快速判断需求价值的能力。贡献域不是给自己贴上的标签，而是我应该用结果去证明、用责任去扩大的一块地方。

我并不因为这些认识而气馁。过去我可能会困惑，自己要怎样才能进步成一个合格的 Co-founder；现在我反而感谢自己努力过、用力过，也犯下过许多错误。错误让我看见了自己的能力边界，也让我知道下一步应该训练什么。

## 致失败之兽：我还没有驯服它

在《做对产品》的前言里，有一句听起来可能有点中二，但我觉得真的很帅的话：

> 致失败之兽：\
> 你教会我不少经验教训，现在换我来驯服你了。

我的热情正在推动我去驯服这头失败之兽。它虽然在我身上留下了很多疤痕，但借助这些疤痕，我反而能更好地找到自己需要训练的能力。

我也学会用这种方式给自己设置精神奖励：这感觉有点像打宫崎英高的游戏，被 Boss 虐了很多遍，最后熟练到能够见招拆招，并且终于把它打败。失败不再只是一个证明我不行的结果，也可以是一张标记着攻击路径的地图。

我仍然会因为给团队添麻烦而感到愧疚。但这份愧疚不应该只用来惩罚自己，它可以被转化成一种具体的愿望：以后和同事共事时，我希望自己不再依靠愧疚驱动努力，而是真正为他们承担更多责任。

我也想更积极地让自己暴露在真实反馈里。比如看到圈内很多人称赞 pi Agent 时，一个不懂它为什么厉害的人，可以先去学习、去实践，最后在一手经验里理解它为什么好。那个最初看起来像盲从的人，反而可能在实践之后真正领悟到 pi Agent 的精髓。

这不是鼓励盲从。相反，如果一个人看到大家都在称赞 pi Agent，就先入为主地认定这只是一次炒概念，然后站在旁边指指点点、说三道四，过了很久也没有真正去理解它为什么好，那么他错过的可能不只是一个工具，而是一次通过实践修正自己判断的机会。

这样的人更像愤青：他未必真的拥有文学气质或独立判断，只是停留在对符号的认同与反认同上。真正的判断力，应该来自自己做过、被现实检验过，也能够承担被别人反驳的可能。

所以我想做的，是先跑起来，先做出东西，再让别人评价，也不害怕别人评价。我可以更积极地让自己受伤，并借此成长——这里的“受伤”不是追求痛苦，而是主动把自己暴露在真实反馈前，并把失败控制在仍然能够恢复的范围里。主动接受小剂量、可恢复的失败，比躲在旁边等待一个足够安全的结论，更可能让人真正获得经验。

## 继续往前走

热情让我出发，错误让我看见边界，责任让我继续。

我希望自己能吸取这段时间的教训，不再害怕犯错，也不再扮演一个温顺听话的人。我想尽快提高自己在能力范围内承担责任的阈值，在成为一个极客的路上继续成长。

我还没有驯服它，但我已经知道它可能会从哪里咬过来，也开始知道自己需要训练什么。
